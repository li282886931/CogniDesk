# 知识库管理与可追溯 RAG 回复技术方案

**日期：** 2026-10-27  
**阶段：** 一期第一阶段  
**状态：** 待审阅

## 1. 目标

建立一个可验证、可追溯的知识库和 RAG 回复闭环：

1. 管理员可以创建、编辑、发布和停用文本知识条目。
2. 只有“已发布”知识可以参与检索和生成回复。
3. 客户问题经过检索后，机器人只能基于命中的知识回答。
4. 每条机器人回复都能展示来源标题、版本和命中片段。
5. 无命中、低置信度、知识过期或模型不可用时，系统必须拒答并建议转人工。
6. 知识变更、发布、停用和机器人引用都写入审计记录。

本阶段不处理 PDF/Word 文件解析、外部渠道接入、复杂 Agent 工具调用和生产级 SSO。

## 2. 当前问题与范围边界

当前系统已经有 Milvus 连接适配器和本地 llama-server 适配器，但二者尚未形成业务闭环：

- `backend/app/vector_store.py` 只能直接搜索已有 collection，没有知识写入、建 collection、删除和版本隔离能力。
- `backend/app/main.py` 的物流回复使用硬编码知识来源，未经过实际检索。
- 知识库没有数据表、管理接口、发布状态和人工核验流程。
- LLM 当前使用非流式请求，无法将检索证据和最终答案结构化返回。

本阶段采用“文本知识条目 + 可替换 embedding 接口 + Milvus 检索”的最小真实闭环。文档上传和解析在后续阶段增加，不改变本阶段的知识条目和检索接口。

## 3. 总体架构

```text
知识管理员
    │
    ▼
知识库管理 API ── MySQL/SQLite: knowledge_items, knowledge_versions
    │                         │
    │ 发布                     │ 审计
    ▼                         ▼
Embedding Provider ──────── audit_events
    │
    ▼
Milvus: 已发布知识向量

客户消息
    │
    ▼
路由器 ── 敏感/负面/人工请求 ──> 转人工
    │
    ▼
Embedding Provider
    │
    ▼
Milvus 检索已发布知识
    │
    ├── 无命中或低置信度 ──> 安全拒答 + 建议转人工
    │
    ▼
本地 LLM
    │
    ▼
回答 + 来源证据 ──> messages + 前端证据面板
```

业务层不直接依赖 Milvus SDK。向量库通过 `KnowledgeVectorStore` 接口隔离，测试默认使用内存实现，运行环境使用 Milvus 实现。

## 4. 数据模型

### 4.1 `knowledge_items`

保存知识条目的稳定身份和当前状态：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `knowledge_id` | `VARCHAR(64)` | 主键 |
| `title` | `VARCHAR(160)` | 知识标题 |
| `category` | `VARCHAR(80)` | 业务分类 |
| `status` | `VARCHAR(24)` | `DRAFT`、`PUBLISHED`、`ARCHIVED` |
| `current_version` | `INT` | 当前发布版本 |
| `created_by` | `VARCHAR(64)` | 创建人 |
| `updated_by` | `VARCHAR(64)` | 最后修改人 |
| `created_at` | `VARCHAR(40)` | 创建时间 |
| `updated_at` | `VARCHAR(40)` | 修改时间 |

### 4.2 `knowledge_versions`

保存不可变的知识版本：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `version_id` | `VARCHAR(64)` | 主键 |
| `knowledge_id` | `VARCHAR(64)` | 所属知识条目 |
| `version` | `INT` | 从 1 开始递增 |
| `content` | `TEXT` | 知识正文 |
| `status` | `VARCHAR(24)` | `DRAFT`、`PUBLISHED`、`ARCHIVED` |
| `source_note` | `VARCHAR(255)` | 来源说明 |
| `effective_from` | `VARCHAR(40)` | 生效时间 |
| `effective_until` | `VARCHAR(40)` | 可为空，失效时间 |
| `created_by` | `VARCHAR(64)` | 创建人 |
| `created_at` | `VARCHAR(40)` | 创建时间 |

同一知识条目只能有一个已发布版本。重新发布时，旧版本先归档，再将新版本设为已发布。

### 4.3 `message_evidence`

保存机器人消息实际使用的证据，避免未来知识内容变化后无法还原当时依据：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `evidence_id` | `VARCHAR(64)` | 主键 |
| `message_id` | `VARCHAR(64)` | 机器人消息 |
| `knowledge_id` | `VARCHAR(64)` | 知识条目 |
| `version` | `INT` | 引用版本 |
| `chunk_text` | `TEXT` | 命中片段 |
| `score` | `DECIMAL(8,6)` | 检索分数 |
| `created_at` | `VARCHAR(40)` | 记录时间 |

## 5. 知识管理 API

所有接口沿用现有统一响应格式 `{code, message, data, request_id}`。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/api/v1/knowledge` | 创建草稿知识 |
| `GET` | `/api/v1/knowledge` | 按状态、分类查询知识 |
| `GET` | `/api/v1/knowledge/{id}` | 查询条目及版本 |
| `POST` | `/api/v1/knowledge/{id}/versions` | 创建新草稿版本 |
| `POST` | `/api/v1/knowledge/{id}/publish` | 发布指定版本并建立向量索引 |
| `POST` | `/api/v1/knowledge/{id}/archive` | 停用知识 |
| `GET` | `/api/v1/knowledge/{id}/evidence` | 查询被回复引用记录 |

### 5.1 发布约束

- 标题、分类和正文不能为空。
- 正文长度限制为 1 至 20,000 个字符。
- 发布前必须存在有效正文。
- 发布操作必须生成新的审计事件。
- 向量写入失败时，数据库状态不能变为 `PUBLISHED`。
- 已发布版本不可直接编辑，只能创建新版本。

## 6. RAG 回复流程

### 6.1 检索

1. 接收客户文本并执行现有敏感意图、人工请求和负面情绪路由。
2. 对非人工消息生成 query embedding。
3. 仅检索已发布知识版本。
4. 返回最多 5 条候选证据，包含 `knowledge_id`、版本、标题、片段和分数。
5. 低于配置阈值的结果视为无命中。阈值通过环境变量配置，默认值为 `0.78`。

本阶段不允许用关键词命中替代 RAG 检索。敏感意图路由可以继续保留规则，但 FAQ 回复必须经过向量检索。

### 6.2 生成

LLM 输入必须明确区分：

- 系统规则：只能依据证据回答，不得补充证据外的日期、价格、订单号、技术参数或政策。
- 证据区：包含来源标题、版本、命中片段和检索分数。
- 客户问题区：原始问题。

生成结果返回：

```json
{
  "reply": "根据当前已发布的物流服务规范，物流状态会在承诺时效内更新。",
  "confidence": 0.91,
  "evidence": [
    {
      "knowledge_id": "kn_123",
      "title": "订单物流服务规范",
      "version": 2,
      "chunk_text": "物流状态会在承诺时效内更新。",
      "score": 0.91
    }
  ],
  "handoff_required": false
}
```

最终回复中不得出现 `<think>`、内部推理或未被证据支持的内容。当前阶段先保持同步接口，但 `LLMClient` 必须预留后续 SSE 流式接口，不把流式协议写死在路由函数中。

### 6.3 安全拒答

以下任一条件成立时，不调用生成模型或丢弃模型结果：

- 没有命中已发布知识。
- 最高检索分数低于阈值。
- 知识已过期或被停用。
- LLM 超时、返回格式错误或输出为空。
- 输出包含无法由证据支持的硬性事实。

安全回复固定表达为：

> 暂未找到可以确认该问题的已发布知识。我可以为您转接人工客服继续处理。

同时将会话转为 `HUMAN_HANDLING`，原因使用 `low_confidence`。

## 7. 前端呈现

本阶段只扩展现有工作台，不做独立后台页面：

- 增加知识库列表和详情视图入口。
- 支持创建草稿、编辑新版本、发布和停用。
- 回复消息旁显示来源标题、版本、命中片段和置信度。
- 对无命中回复显示“待人工处理”，不显示虚构的知识来源。
- “核验知识来源”按钮打开证据详情，而不是静态提示。

现有静态“退款申请服务规范”和固定客户画像不能继续作为真实 API 成功后的展示数据；只有 API 不可用的本地预览模式可以保留，并必须标识为预览。

## 8. 错误处理与一致性

- 知识数据库写入和向量索引写入采用发布事务边界：索引失败则回滚发布状态。
- 向量库不可用时，知识可以保存草稿，但禁止发布。
- 重复发布同一版本返回幂等成功，不重复写入索引和审计。
- 对不存在的知识、版本和会话返回 404。
- 对非法状态转换返回 409。
- 所有异常响应保留 `request_id`，日志不得输出知识正文中的敏感信息。

## 9. 测试策略

### 后端单元测试

- 创建知识默认进入 `DRAFT`。
- 发布只允许有效草稿版本。
- 已发布版本不可直接修改。
- 向量索引失败时发布状态回滚。
- 检索只返回已发布知识。
- 分数低于阈值时返回安全拒答并转人工。
- 有证据时回复包含来源、版本和证据片段。
- 模型输出中的 `<think>` 被移除。
- 知识发布、停用、引用写入审计记录。

### API 集成测试

- 完整执行“创建知识 → 创建版本 → 发布 → 创建会话 → 客户提问 → 回复引用”流程。
- 验证停用知识不能继续被检索。
- 验证 Milvus 不可用时草稿可保存、发布失败。

### 前端测试

- 知识列表正确显示状态。
- 发布和停用操作显示成功/失败反馈。
- 机器人消息显示真实证据而不是静态来源。
- 无命中时显示转人工状态。

## 10. 实施顺序

1. 抽象知识数据模型和数据库表，先补后端失败测试。
2. 实现文本知识 CRUD、版本和发布状态。
3. 扩展向量存储接口，增加内存测试实现和 Milvus 实现。
4. 接入 embedding provider，并完成发布时索引。
5. 将客户消息 FAQ 路由改为检索优先，保存消息证据。
6. 补充安全拒答、低置信度转人工和审计查询。
7. 实现前端知识管理和证据展示。
8. 运行后端测试、前端测试、构建和端到端流程验证。
